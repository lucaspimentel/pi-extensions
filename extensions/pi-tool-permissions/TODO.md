- [x] Implement a `readonly-awk` bash validator (2026-09-29)
  - Done: `validateReadOnlyAwk` in `rules.ts`, registered as `BASH_VALIDATORS["readonly-awk"]` and default-on via `awk -> "readonly-awk"` in `DEFAULT_BASH_VALIDATORS`; documented in the `index.ts` header block and `README.md` (which no longer names plain `awk` as unbuilt), covered by new tests in `test-validators.mjs` (registry, direct reason, decide-level allow/decline, read roots, defaults/`none` sentinel, compounds) and the updated default-map assertion in `test-loadconfig.mjs`.
  - Follow the `bashValidators` framework (see the completed duckdb/mlr item above): implement `validateReadOnlyAwk(tokens, cwd, readRoots)` in `rules.ts` alongside `validateReadOnlyDuckdb` / `validateReadOnlyMlr` (~1281 onward), register it in `BASH_VALIDATORS` and add `awk: "readonly-awk"` to `DEFAULT_BASH_VALIDATORS`, and document it in the `index.ts` header block, `README.md` (which already names "plain `awk`" as a possible future validator), and `pi-tool-permissions.example.json`.
  - Risk surface inside the single-quoted program text: `system(...)`, `getline` (from file or command), output redirection (`print > "file"`, `print >> "file"`, `print ... | "cmd"`, `|&` coprocess), gawk `@include` / `@load` (dynamic code). Shell-level `>` redirects are already screened by `stripExemptRedirects` before tokenization, like the other validators.
  - Proposed rules: whitelist flags only (`-F` arity 1 is a field-separator regex, safe; `-v` arity 1 but the value must be a simple constant: reject `(`, backticks, `|`, `>`, `system`; `-e` arity 1 is program text to scan), reject `-f` / `-i` / `-l` / `-E` / `--exec` / unknown flags (program loaded from a file is unscannable; gawk `-i`/`-l` load code). Fail-safe on comparison ambiguity: `>` and `|` are common inside regexes and numeric comparisons (`$1 > 5`), so only reject when followed by a quote or `&` (e.g. `> "`, `| "`, `|&`) and accept the rare false positive as a prompt.
  - Positional arguments: input files must pass `looksFileish` + `pathInsideAllowedRoots` (cwd/read-root containment, covers `/etc/passwd`-style reads); reject `var=value` positional assignments outright (POSIX parses them as full assignment expressions, which can invoke functions). Zero program text (e.g. only flags) should decline, mirroring duckdb's no-SQL decline.
  - Fail-open semantics: validator can only convert would-be-ask into allow by proving read-only; anything unprovable falls through to the normal pipeline. Tests in `test-validators.mjs` (happy paths, each rejected construct, path containment, flag vetoes) plus a decide-level default test.

- [x] Implement a `readonly-find` bash validator (2026-09-29)
  - Done: `validateReadOnlyFind` in `rules.ts`, registered as `BASH_VALIDATORS["readonly-find"]` and default-on via `find -> "readonly-find"` in `DEFAULT_BASH_VALIDATORS`; documented in the `index.ts` header block and `README.md`, covered by new tests in `test-validators.mjs` (registry, direct reason, decide-level allow/decline, read roots, defaults/`none` sentinel, compounds) and the updated default-map assertion in `test-loadconfig.mjs`.
  - Motivation: the user-level `Bash(find *)` allow wildcard auto-allows destructive primaries (`-delete`, `-exec`, `-execdir`, `-ok`, `-okdir`), which currently requires belt-and-braces `ask` rules in `~/.pi/agent/pi-tool-permissions.json` (`find * -delete*`, `find * -exec *`, `-execdir`, `-ok`, `-okdir`; note the matcher's `" *"` → optional `( .*)?` quirk in `compilePattern`, `rules.ts` ~1721, makes trailing ` *` and bare `*` near-equivalent). A validator proves read-only statically instead, and also covers compound commands per-subcommand via `validatorApprovedBashReason`.
  - Same framework as the awk item: `validateReadOnlyFind(tokens, cwd, readRoots)` in `rules.ts`, registered in `BASH_VALIDATORS` + `DEFAULT_BASH_VALIDATORS` (`find: "readonly-find"`), documented in `README.md` and `pi-tool-permissions.example.json`, tests in `test-validators.mjs`.
  - Proposed rules: reject the write/execute primaries `-delete`, `-exec`, `-execdir`, `-ok`, `-okdir`, and the output-writing primaries `-fls`, `-fprint`, `-fprint0`, `-fprintf`; reject `-f`-style program-loading is N/A but note `-newerXY`/`-anewer`/`-cnewer` reference files that should get the `looksFileish` + `pathInsideAllowedRoots` containment check, as should all positional starting paths. Unknown primaries starting with `-` should decline (fail-safe, like duckdb's unknown-flag rule) rather than trying to enumerate the full read-only set; global options (`-maxdepth`, `-mindepth`, `-name`, `-type`, `-mtime`, etc.) pass. `-fstype` is a harmless filter, not a mount operation.
  - Shell-level redirects to files are already screened upstream; `| xargs rm` pipelines are split per-subcommand by the existing compound-command machinery, so `find ... -print0 | xargs -0 rm` prompts via the `xargs` half regardless. Fail-open semantics as above; add decide-level default tests too.
